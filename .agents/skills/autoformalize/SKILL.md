# Autoformalize

Turn the requested mathematical source into faithful, kernel-checked Lean proofs. Continue through the agreed targets; a plan, statement scaffold, or collection of helpers is not a completed formalization.

## Step 0: create the recurring wake-up job before anything else

The very first action of every invocation of this skill, whether an initial request, a resumption, a bare `continue`, or a scheduled wake-up, is to ensure the recurring 15-minute wake-up job described in "Keep a recurring wake-up until the task is finished" below exists. Do this automatically and immediately, without asking, before task discovery, reading the source, bootstrapping the repository, or editing any file. When the targets or destination files are not yet known, create the job with a provisional prompt naming the repository and the user's request, then update or replace it (never duplicating it) once `automation/instructions.md` records the exact targets. ## Generic file and namespace requirements

- Machine-generated Lean formalization files follow the **paper-structured layout** described in "Paper-structured layout and statement scaffold" below: inside the library source folder (e.g. `Project/`), one folder per source paper, one folder per section, one file per subsection (one file per theorem in the introduction). This layout replaces the former `Auto/` folder and single-file default; an existing project that already uses an `Auto/` folder keeps it unless the user asks for the paper-structured layout. The layout is a standing authorization for exactly the files it prescribes (plus the top-level import file, the project configuration, the `automation/` records and `sources/`).
- Create other new files only as authorized by the user. Check the current request and applicable user-approved instructions for existing authorization; do not ask again when the file is already covered. This applies to supporting files and scratch files as well as permanent Lean files. Suggested layouts other than the paper-structured layout do not themselves authorize file creation; the project-configuration and reusable-prerequisites clauses below are explicit standing exceptions. If a necessary file is not covered by authorization or those exceptions, identify its exact proposed path and purpose and ask for the missing authorization before creating it.
- **Hard limit: no Lean file may be longer than 10,000 lines.** This applies to every Lean file, including reusable-prerequisite files and existing files you extend; if a subsection file would exceed it, split it further along the source's next-level boundaries (`<k>_<m>_<p>_<Short_Name>.lean` per subsubsection), never through a single source result.
- All Lean code you write must be in `namespace Auto ... end Auto` (in the paper-structured layout: `namespace Auto.<PaperTag>`), including helper declarations and proofs. Use the namespace `Auto`, not `Codex`, `Claude` or the project's own namespace; do not introduce other subnamespaces unless specified by the user. In the paper-structured layout each paper gets its own subnamespace `Auto.<PaperTag>` (e.g. `Auto.DIR`, `Auto.DIRX`), matching its folder; declaration names carry no paper prefix (`Auto.DIR.thm_1_1`), and a later paper reusing an earlier one's definitions opens the earlier namespace (`open Auto.DIR`). File headers and imports necessarily precede the namespace. If a requested edit conflicts with this rule or a protected existing interface, resolve the conflict rather than silently moving or renaming the user's declarations.

## Reusable prerequisites: standing file-creation exception

When the argument needs a substantial general fact unavailable in the repository or its dependencies, create exactly one dedicated Lean file directly in the library's `Prerequisites/` folder (e.g. `Project/Prerequisites/NamedTheorem.lean`; in a legacy `Auto/` project, directly in `Auto/`) for that reusable prerequisite, never in a deeper subfolder. This is user-authorized as an exception to the single-file default and the restriction on creating files; do not request additional confirmation when its conditions are defensibly met. It retains the `Auto` namespace, generation notice, and proof-verification requirements.

Establish and document why the exception applies before creating the file:

- **Needed and missing:** Identify the exact project use case(s) and search the repository and pinned dependencies for the fact, including equivalent formulations. Reuse or adapt an adequate existing result instead of duplicating it. A missing wrapper or inconvenient theorem name is not a missing substantial theorem.
- **Substantial and general:** Give a defensible mathematical reason for a separate reusable development. Useful tests are whether the result has a generally accepted name, or whether explaining it would take roughly a full university lecture and it is likely to appear in a university textbook or lecture notes. These are indicators of mathematical substance, not a requirement that both tests hold. Lengthy Lean bookkeeping or an invented name does not by itself qualify.
- **Exactly one file per qualifying prerequisite:** Choose a descriptive theorem-based filename directly in that folder, such as `Project/Prerequisites/NamedTheorem.lean`. No subfolders and no companion files are allowed for the prerequisite. The only exception is the 10,000-line limit: if the prerequisite's development would exceed it, split it into consecutive files directly in that folder named after the theorem and the part of its textbook proof they contain (e.g. `Prerequisites/NamedTheoremDecomposition.lean`, `Prerequisites/NamedTheorem.lean`), and justify the split in its `Status.md` section. Put the theorem and all definitions and supporting lemmas newly developed specifically for it in that one file. Reuse the same file for every project application. A mathematically distinct substantial missing theorem may qualify separately, with its own justification and exactly one file; do not relabel stages of one prerequisite's proof as separate instances to evade this limit.

Seek a reusable, reasonably general formulation of the kind expected in a textbook. State meaningful hypotheses and conclusions independently of incidental paper-specific constructions, and expose a theorem usable by other developments. The prerequisite theorem's statement must depend only on Mathlib (including its Lean foundations) and definitions local to that same file. This includes types, implicit parameters, typeclasses, and definitions appearing in its hypotheses and conclusion. Local definitions must themselves use only Mathlib or definitions in that file; wrapping an imported project-specific definition in a local alias does not satisfy the restriction. The statement must not depend on declarations from the main formalization, other project files, or other dependencies outside Mathlib. Proofs may reuse already proved results without introducing their project-specific vocabulary into the statement.

The formulation must cover at least every use case needed in this project; prove the specializations or bridges that establish this in the consuming project file, keeping the reusable statement independent of those applications. Avoid both a narrow theorem hard-wired to one application and speculative generality that does not serve a reasonable textbook formulation. Keep its import dependencies independent of the main proof module so that the main formalization can import and apply it without a cycle.

The file's Lean module docstring (`/-! ... -/`, after the header and imports, beginning with the required generation-notice paragraph) must name and explain the theorem, describe the mathematical formulation and hypotheses, and give verified references. Identify textbook, lecture-note, or original-source locations precisely where available, with useful links; do not invent citations. Keep the required generation notice as the first paragraph of that docstring, after the linter-compliant header. Prove the reusable result completely under the same source-fidelity and axiom standards as the main work. Before recording completion, inspect the elaborated statement and its local definitions for the required dependence on Mathlib/local definitions only; an axiom audit alone does not establish this. Then return to the dependent project step.

In `automation/Status.md`, put a dedicated section for each reusable prerequisite immediately after the lines for the main theorem statements and before any main-proof lines. Order prerequisite sections and their proof steps by their own dependencies. Each section must contain a concise justification for invoking this exception (need, missing library coverage, mathematical substance, chosen generality, and file path) and fine-grained timestamped status rows, one per source-tied step, tracking the work and remaining proof obligations. Record this when opening the prerequisite, and update it as work advances; file creation or a theorem statement alone is not completion. This required justification belongs in `Status.md`, even when ordinary source rows otherwise contain no explanatory prose.

## Required machine-generation notice

Machine-generated source files must carry this exact notice at the top, using the file format's comment syntax (for Lean files: as the first paragraph of the module docstring directly after the linter-compliant header and imports, as specified below):

```text
This file was automatically generated by Codex.
```

Every machine-generated Lean file must begin with a header that passes Mathlib's header linter (`Mathlib.Tactic.Linter.Header`, part of `weak.linter.mathlibStandardSet`), in exactly this shape:

```lean
/-
Copyright (c) YYYY Holder Name. All rights reserved.
Released under Apache 2.0 license as described in the file LICENSE.
Authors: Codex
-/
module

public import Mathlib

/-!
# Title of the file

This file was automatically generated by Codex.

…module documentation…
-/

@[expose] public section

namespace Auto
…
end Auto
```

1. Line 1 is `/-` alone. The last header line is `-/` alone. No blank line, comment, or other content precedes line 1.
2. Line 2 is the copyright line: `Copyright (c) YYYY`, exactly one space, the copyright holder's name (the user's name), then `. All rights reserved.` A year alone is insufficient.
3. Line 3 is the license line, exactly as the linter expects: `Released under Apache 2.0 license as described in the file LICENSE.` for Apache-licensed projects; make sure the root `LICENSE` file it cites exists (the bundled Apache 2.0 text). For a project under a different license, keep its actual license text and set `linter.style.header.license` in the Lake `leanOptions` to that exact line.
4. Line 4 is the authors line `Authors: Codex`: no trailing period, no ` and `, no double spaces; separate several authors with `, ` (keep existing human authors of an existing file, appending `Codex`).
5. Use Lean's module system from the start: the header is followed directly by the line `module`, then a blank line, then the imports, all written `public import …` (Mathlib and the project's own modules). The module docstring (`/-! … -/`) follows the imports, and `@[expose] public section` follows the docstring so that definitions and their bodies are exported; put `namespace Auto` after it. The module docstring's first paragraph after the `#` title is exactly the sentence `This file was automatically generated by Codex.` (the sentence ends with a period, so it must not be placed in the `Authors:` line or elsewhere in the header).

Preserve the project's actual copyright holder, year, license, and existing legal attribution; do not invent legal information or relabel human-authored material as wholly machine-generated. Use the user's established name from explicit instructions or reliable project attribution; do not substitute the agent name, a guessed name derived from a directory/login, or an unfilled placeholder, in the copyright line. If the name cannot be established, ask for it before finalizing the header. When checking the header, verify that the copyright line actually contains the user's name, not merely a copyright symbol and year, and that the file compiles without header-linter warnings (e.g. `lake env lean -Dweak.linter.mathlibStandardSet=true File.lean`).

## Paper-structured layout and statement scaffold

The formalization mirrors the source paper(s) file by file and declaration by declaration, so that a reader can follow the paper and the Lean code side by side. These rules apply unless the user specifies otherwise.

**Layout.**
- Inside the library source folder, one folder per source paper, named by a short tag (the user's tag, otherwise the citation key, e.g. `DIR`, `DIRX`), and inside it one folder per top-level section named `<k>_<Section_Name>` (appendices `A_<Name>`, ...).
- The introduction folder contains one file per theorem in a theorem environment, `Thm_1_1.lean`, `Thm_1_5.lean`, ... Corollaries are placed in the file of the theorem they follow from (with a comment recording their original position). Introductory text preceding a theorem (since the previous theorem's discussion) and the discussion following it belong to that theorem's file; text after the last theorem (structure of the paper, acknowledgments) goes at the end of the last file.
- Every other section has one file per subsection, `<k>_<m>_<Short_Name>.lean`. Text of a section before its first subsection goes into `<k>_0_<Section_Name>.lean` if it contains definitions or claims, otherwise into a comment at the top of the first subsection file. A section without subsections is a single file `<k>_0_<Section_Name>.lean`. Subsubsections and unnumbered paragraphs such as "Case I" become Lean `section`s with a `/-! ### ... -/` heading.
- Names are shortened by dropping articles, prepositions, conjunctions and similar filler words while keeping the key words, capitalized and joined by `_` (e.g. "Properties of the function J" → `2_2_Properties_J.lean`, "Proof of the two-point inequality" → `6_Proof_Two_Point_Inequality`). Subsections without mathematical claims still get their file, containing comments.
- Each file imports only the earlier files (in paper order) whose declarations it uses; the top-level import file imports all of them. Module paths with leading digits use guillemets.

**Content and order.**
- Follow the paper's order exactly; all content of the paper is represented in the files, in the original order and wording.
- Every definition, lemma, proposition, theorem, corollary, fact and remark with mathematical content becomes a Lean declaration: definitions (also those made inline or outside a definition environment, including auxiliary functions and tight lower bounds of computer-assisted arguments) become `def`s, and every mathematical claim (numbered or not, displayed or inline, in an environment or not, including each step claimed inside a proof, each numerical evaluation and each computer-verified inequality) becomes a `theorem`. Conjectures become `def ... : Prop` and are not claimed. Purely heuristic or numerical-evidence statements stay as comments. Precise claims cited from the literature are stated too (docstring "cited from ...").
- Every declaration has a docstring with the precise mathematical formulation from the paper (KaTeX `$...$`, so that it renders in the documentation) and the precise location: the number when there is one (`[DIR], Lemma 5.4`, `[DIR], (2.9)`), otherwise the (sub)section and enclosing proof (`[DIR], proof of Lemma 6.4`). Mark computer-verified claims as the paper does.
- Purely descriptive paper text is not copied into comments (unless the user asks for it); the mathematical content lives in the declarations and their docstrings, and module docstrings say which part of the paper a file covers.
- The introduction folder, and any section whose definitions are needed by files that its own theorems depend on, gets a `Definitions.lean` holding the definitions (and the elementary facts about them needed elsewhere), so that theorem files can import the files containing their proofs.
- Each proof environment becomes `section Proof_Lemma_2_3 ... end Proof_Lemma_2_3` (`Proof_Theorem_1_6`, `Proof_Proposition_3_3`, ...), containing the claims of the proof as theorems and the remaining proof text as comments; sub-proofs such as "Proof of (1)" become nested sections `Proof_Claim_1`.
- Take theorem and equation numbers from the compiled paper (PDF), not from counting TeX environments: macros can skip or shift numbers.

**Names and notation.**
- Each paper's declarations live in the namespace `Auto.<PaperTag>`. Lean names of numbered results follow the paper, without a paper prefix: `thm_1_1`, `lemma_1_2`, `prop_2_1`, `cor_2_5`, `rem_2_3`, `eqn_2_4`, `conj_1_4`. Claims without a name or label get descriptive names consistent with the Mathlib naming conventions.
- Definitions are named as suggestively as possible after the paper's notation (`L`, `Q`, `J`, `b`, `G₁`, `w₀`); when a later paper opens an earlier paper's namespace and a definition name would be ambiguous, the later one uses a suffix (`LX`) and restores the paper's look with `local notation` in each of its files.
- Statements must be mathematically faithful to the paper and handle Lean's conventions explicitly: junk values of division, `Real.log`, `Real.sqrt`, `Real.rpow` (`0 ^ 0 = 1`), `sInf`/`sSup` of empty or unbounded sets (in `ℝ`, use one `sInf` over a set rather than nested `⨅` with `Prop` binders), functions only meaningful on part of their domain (state the domain hypotheses), objects defined by a characterizing property (define with `Classical.choose` or an inverse and state the existence/uniqueness claim as a separate theorem, adding implicit conditions such as nonnegativity and recording them).
- Statements should look as close as possible to the paper, except where a Lean idiom is clearly preferable: write reciprocals as `x⁻¹`, not `1 / x`, including numerals (`2⁻¹`, not `1 / 2`). Conservatively introduce simple notation where needed, at its first use in the paper, and list it in the module docstring of the file introducing it. Do not introduce notations whose tokens contain `_` (such as `h_{A}`); use plain Lean functions with the arguments applied (`h A`) instead. Notation may only be introduced with the `notation` and `notation3` commands (including `local notation`); never write metaprogramming code (`syntax`, `macro`, `macro_rules`, `elab`, `meta def`, custom elaborators) for notation or anything else. Check that notation does not clash with Mathlib tokens or common syntax (a leading `|`, for example, breaks set-builder notation; use a visually similar unused symbol such as the full-width bar `｜` instead).

**Forward reasoning.** Within a file every declaration must come after all its statement and proof prerequisites (by the paper's argument); where the paper states a result before its proof, move the statement after the `section Proof_…` (the minimal change), and move claims to the file containing their proof ingredients when necessary. Each file imports every file containing a prerequisite; there must be no import cycles. Files therefore need not be imported in paper order. Verify this on the declaration-level dependency graph.

**Phases.**
- *Setup phase*: create the layout, state every definition and claim, and prove every claim `by sorry`; do not attempt proofs. The project must build with only `sorry` warnings and the header/style linters must pass. `automation/Status.md` records the scaffold status per file; fine-grained proof rows are added when the proof phase begins.
- *Audits after the setup phase*: (1) record every discrepancy between paper and formalization in `automation/ErrorReport.md` and, at the place where it occurs, in a docstring paragraph starting `**Discrepancy with the paper.**` that states precisely what the paper says, what the problem is, and what the Lean statement does instead; (2) audit every statement for faithfulness (quantifiers, domains, constants, junk values, completeness) and fix it; (3) audit strict forward reasoning by analysis of the paper's arguments: in `automation/forward_reasoning.md`, list every claim that appears (in paper/file order) before prerequisites of its proof, and determine whether the resulting proof dependencies force import cycles between files, describing how the proof phase must resolve them.
- *Proof phase*: replace the sorries in forward logical order as described in "Work in strict forward logical order". Proofs of results stated early whose proofs appear later in the paper (e.g. theorems of the introduction proved in a later section) need later results; when this requires restructuring imports or moving statements, record the plan in `instructions.md` and ask the user if it changes the paper-structured layout.

## Work in strict forward logical order

Read the proof of each target and identify its actual dependency DAG. Before implementing that target's proof, record the substantial steps in a forward topological order: every prerequisite precedes its consumers. Source page order and theorem numbering identify locations, not proof order. Mark shared foundations and independent branches clearly; close every incoming dependency before starting a join.

Unless the user specifies otherwise, work through the proof-work line items of `Status.md` consecutively in their established logical order, completing one before advancing to the next. The main theorem statement rows at the top are an overview, not an instruction to prove a conclusion before its prerequisites. Select the next unfinished work item whose prerequisites are proved; do not bypass a difficult unfinished item for easier downstream work. Keep one item active at a time by default. If a missing prerequisite emerges, apply the reusable-prerequisites clause when it qualifies; otherwise keep it in the main authorized file. Insert it before its consumer, finish it, and return to the selected item. Introduce helper lemmas only when they serve that item. Avoid accumulating speculative foundations, downstream wrappers, or several unfinished branches. A dependency DAG does not itself request extra agents or concurrent work.

For each item:

1. Read its full statement, proof, and invoked references. Search the repository and the pinned Mathlib sources for matching definitions and theorems before implementing replacements. Verify their hypotheses and normalization conventions. If a cited prerequisite has no available Lean proof, formalize the needed result; a literature citation cannot replace a Lean proof.
2. Choose a Lean statement matching the source's objects, quantifiers, assumptions, ranges, and conclusion. Apply the checks in [references/source-fidelity.md](references/source-fidelity.md) when translating a new statement or auditing a suspect one.
3. Prove the item, adding only the needed supporting material. Follow the source's mathematical argument while allowing equivalent Lean organization and verified reuse. Document substantive changes of proof route. A shortcut cannot count as completion of omitted source steps that remain in the agreed scope.
4. Compile the edited source and its dependencies as you iterate. Verify the whole project and the relevant axiom dependencies before marking a source item complete. Update its ledger status immediately, then select the next ready item.

Continue automatically from one completed line item to the next. Unless otherwise specified by the user, stop only once all main theorem(s) in scope are fully proved, the required project checks pass, and their transitive axiom dependencies are a subset of `propext`, `Classical.choice`, and `Quot.sound`. Do not stop after a milestone, useful prerequisite, or partial proof to ask whether to continue. The mandatory stop for a discrepancy requiring a change to a main result, described below, is an exception. If execution is interrupted, preserve the exact current state and resume the next logical item when execution resumes; interruption or handoff is not completion.

Work proceeds in two phases (see "Paper-structured layout and statement scaffold"). In the **setup phase** every declaration is stated and proved `by sorry`; this scaffolding is authorized whenever the user asks to set up the repository or state the theorems, and no proofs are attempted. In the **proof phase** the sorries are eliminated in forward logical order without introducing `admit` or new axioms; new helper lemmas are proved as they are introduced. Keep remaining placeholders visible and report them; eliminate those required by the final scope. Existing authorized out-of-scope sorries are not an invitation to delete or change their targets.

## Report discrepancies and stop when a main result must change

Record every discrepancy between the formalization and its source in `automation/ErrorReport.md`, including corrected errors, different constants or hypotheses, convention differences, and substantive departures from the source argument. Add a timestamped entry when the discrepancy is discovered. Very briefly state the exact source location, what differs, and how it was resolved. If unresolved, say so explicitly and add a timestamped resolution when known; do not imply that a proposed fix has been proved. A short entry is sufficient; keep lengthy analysis in the relevant proof documentation.

If a discrepancy can only be fixed by changing the mathematical content of a main result, **stop the autoformalization, report the obstruction, and ask the user what to do next**. Record the issue and preserve accurate incomplete statuses, but do not change the main statement or continue other proof branches while waiting for the user's direction. This applies to changes in the intended objects, hypotheses, quantifiers, range, or conclusion. Fixing an incorrect Lean translation to match the unchanged intended source theorem, or repairing an unambiguous typo without changing its mathematical meaning, does not trigger this stop; document the fix and continue in logical order. An uncertain substantive repair also needs clarification before it is adopted.

## Preserve the mathematics and its provenance

- Completion requires the intended source claim. A weaker estimate, restricted parameter range, stronger assumption, different operator, unproved bridge, or theorem assuming its own conclusion does not finish that claim. A stronger intermediate theorem is useful once its specialization to the source theorem is actually proved.
- Reuse established mathematical notions. Add auxiliary definitions when needed for the proof, but never redefine the target into a triviality or hide the missing mathematics inside an assumption or structure field.
- Check semantic side conditions explicitly. Lean's totalized operations can make an apparently faithful formula vacuous or change its meaning; measurability, finiteness, nonzero denominators, and nonempty domains must reflect the actual source contract, not serve as convenient extra restrictions.
- Repair clear transcription or typographical errors conservatively and record the discrepancy and resolution in `ErrorReport.md`. Apply the mandatory stop above when a main result's mathematical content must change. Routine omitted details supplied faithfully are proof obligations, not discrepancies by themselves.
- Use source-based names and document the exact source label/location on the corresponding declaration. Source theorems, lemmas, propositions, corollaries and all other claims become Lean `theorem` declarations. Put the mathematical statement in the theorem's own docstring, not in a related constant or definition. Helper docstrings explain their purpose and point to the source result. Do not copy source proofs into statement docstrings; the text of a proof goes, verbatim, into comments inside its `section Proof_...`, interleaved with the claims it makes.
- Apply the linter-compliant header and the exact machine-generation notice (first paragraph of the module docstring) specified above, preserving existing legal attribution.
